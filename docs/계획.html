04 · Survey · Recommendation

설문 · 추천 방향

VS(빵 MBTI) 초안은 surveyConfig.js에 반영·동작중. 알고리즘 설계는 사용자 몫 — 여기선 데이터로 가능한 방향과 결과 해석만.

VS 문항 초안 (반영됨)

축VS가중치
Q1 맛🍰 달달 vs 짭짤 🥖dessert+3 / meal+3
Q2 탐험⭐ 명물 vs 동네 🔍famous+3 / value+2·meal+1
Q3 상황🚶 혼자 vs 함께 ☕value+1·meal+1 / mood+3·dessert+1
Q4 형태🍽️ 바로 vs 선물 🎁mood+1 / togo+3·famous+1
정보이득: Q2·Q4가 관광객↔현지인/자기소비↔선물을 가장 잘 가름. Q1은 오프너. 2문항(Q1·Q2)만으로도 추천 가능.

데이터로 가능한 추천 방향 (선택지)

방향쓰는 데이터상태
콘텐츠 가중합(태그·점수)설문 태그 · 빵집 태그동작중
메뉴 기반 태그 강화detailIntro2 firstmenu·treatmenu (실값 확인: 튀김소보로 등)가능·미적용

결과값 해석 (방향만)

  • 설문 결과값 = 태그별 가중치 벡터 {dessert:7, mood:6, …}
  • 빵집 점수 = (빵집 태그)·(가중치) 합 → 클수록 적합. 동점 처리(다양 vs 1순위)는 해석 선택지.
  • 트리/적응형·학습형 추천은 데이터 쌓인 뒤 선택지 — 지금은 설계 안 함.

07 · Direction

핵심 방향 — 빵 + 명소 + 경로

비중 A+C 채택. 한 줄 비전: "대전의 빵과 관광 명소를 잇는, 취향 기반 추천 + 경로 지도". 빵만 점 찍는 지도가 아니라, 취향(트리)으로 추천하고 동선(그래프)으로 묶는다.

채택: A + C

A. 상세·명물 백본
빵집 좌표 밀도는 카카오(수백 곳), 관광공사 등재 빵집엔 풀상세(영업·주차·메뉴) + 명물 인증. 깊이로 승부.
C. 호출 확장 (명소 연계)
관광공사 관광지·시장·축제(locationBasedList2 등)와 방문자수(#18)까지 끌어와, 빵을 관광 동선에 얹음.

맵에 무엇을 표시하나 (레이어)

레이어소스 · 대전 수량역할

08 · Graph Algorithm

그래프 알고리즘 — 경로 추천

현재 위치에서 빵집과 명소를, 실시간 교통과 이동수단까지 고려해 최적 동선으로 추천한다. 하루치 빵 투어 코스를 만드는 기능이다. 단계별 상세는 알고리즘설계.html에서 다룬다.

8.1 그래프 = 장소(노드) + 길(엣지) + 비용(가중치)

동그라미(노드)=장소, 선(엣지)=두 장소 사이 길, 선의 숫자(가중치)=이동시간/거리. "그래프 알고리즘"은 이 그림 위에서 길을 고르는 방법. 빵집 지도가 딱 이 그림.

8.2 지도 내비는 어떤 알고리즘을 쓰나

Dijkstra·A* → 실서비스 내비는 CH(전처리 지름길)·실시간 교통(time-dependent)·대중교통(RAPTOR)으로 즉답한다. 즉 "두 지점 빠른 길 + 실시간 교통"은 내비 API가 이미 해결한 영역이다. 원리 복습은 알고리즘설계.html의 ＋내비 알고리즘 심화 탭에서 다룬다.

8.3 ⭐ 그래서 분담 — 내비 엔진은 API, 우리는 "순회+가중치+모드"

① 두 지점 최단/실시간 이동시간 = 카카오 길찾기/모빌리티 API에 맡김 (CH·실시간교통·도보/차/대중교통 다 내장).
② 우리가 직접 설계할 것 = ⒜ 여러 곳을 어떤 순서로 돌까(순회·TSP) ⒝ 취향·혼잡을 가중치로 ⒞ 이동수단 선택 로직. → 이게 우리 차별화 영역.

8.4 우리 경로추천 설계

노드·엣지·비용
  • 노드: 현재위치 + 추천 빵집 상위 N + 주변 명소(관광공사)
  • 엣지 비용: 카카오 API 실시간 이동시간(선택한 이동수단)
cost(i→j) = α·이동시간(API,실시간)
  + β·혼잡패널티 − γ·취향점수 − δ·영업가능
순회 알고리즘 (방문 순서)
상황방법
"지금 가까운 곳"현재위치 기준 NN 1-step
코스 3~7곳NN → 2-opt(꼬임풀기)
코스 ≤~12곳 최적Held-Karp(DP)
이동수단도보/차/대중교통 각각 API → 빠름·편함·저렴 비교 제시

8.5 고도화 · AI

아이디어필요 데이터현실 평가 (정직)
실시간 교통량 예측(시계열·ML)도로별 시간대 교통 이력카카오가 이미 함 우리 직접은 데이터 없음 → API값 사용
학습형 동선 선호
(사용자가 선호하는 코스 학습)		사용자 코스 선택·완주 로그데이터 누적 후 지금 0(콜드스타트)
강화학습(RL) 동선 최적화대량 시뮬·보상설계연구 레벨·과함 공모전엔 부적합
가중치 튜닝 + 규칙형 멀티모달좌표·API·취향(보유)현실적 차별화 지금 가능 · 설명가능
정직한 한계: "내비 알고리즘을 처음부터" = 비현실. 우리 차별화 = API를 똑똑하게 조합 + 취향/혼잡 가중치 + 순회 최적화 + 멀티모달 비교. 학습형(선호·GNN)은 행동 데이터 쌓인 뒤 "발전성"으로.
📌 결정: 코스 3~5곳 기준으로 NN + 2-opt 채택. 멀티모달 비교는 가중치 튜닝과 함께 진행. 혼잡 반영과 학습형은 다음 단계로 분리한다.

09 · Tree Algorithm

트리 알고리즘 — 취향 추천

설문 답을 분석해 만족도 높은 빵·빵집을 더 정확히 추천한다. 정확도를 높이려면 추가 데이터가 필요하며, 그 데이터 그림까지 정리한다.

9.1 결정트리(Decision Tree)란? (아주 기초)

질문으로 가지치기 하며 답을 좁히는 것. 예:
달달? ──예→ 명물? ──예→ 성심당(케이크)
          └아니→ 동네 디저트집
  └아니(짭짤)→ 혼자? ──예→ 소금빵 테이크아웃 …
지금 recommend.js의 "태그 가중합"은 가장 단순한 트리(규칙)의 일종.

9.2 적용 단계 — 점점 똑똑하게

단계방식필요 데이터지금?
L1 규칙 트리손으로 분기 설계 (현재)없음동작
L2 정보이득 적응형
(ID3/CART)		남은 후보를 가장 잘 가르는 질문을 다음에 제시 → 질문 수↓·정확도↑·설명가능빵집 속성 분포(보유)가능
L3 학습형 트리
(랜덤포레스트 등)		"어떤 답 조합 → 어떤 빵집에 만족"을 데이터로 학습사용자 피드백 라벨(다량)데이터 후
L4 협업필터/임베딩"비슷한 취향 사람이 좋아한 집" / 빵집 벡터 유사도상호작용 행렬·임베딩데이터 후

9.3 ⭐ 만족도↑의 핵심 = 피드백 루프

추천 후 "이 추천 맘에 들었나요? 👍/👎" → 그 라벨을 모아 트리/모델을 재학습. 이게 정확도가 오르는 근본 원리. 설문(입력) + 피드백(정답)이 쌍으로 쌓여야 "정확한 분석"이 됨.

9.4 추가로 필요한 데이터

필요 데이터왜어디서
빵집 풍부 속성
(메뉴·가격·분위기·리뷰)		취향과 매칭할 "특징"이 많아야 정교관광공사 detailIntro2(메뉴) · 카카오 · 리뷰
사용자 피드백
(클릭·찜·👍/방문)		"정답 라벨" = 학습의 연료자체 로깅(localStorage→백엔드)
맥락(시간·동행·날씨)같은 사람도 상황 따라 다름설문/센서/시간
🤖 AI 연계 (실제 가능·차별화): 빵집 메뉴·리뷰 텍스트를 LLM/임베딩(예: Claude API)으로 분석해 "달달함·식사성·분위기" 같은 특성 점수로 벡터화 → 추천 피처로. 휴리스틱 태깅보다 훨씬 정밀. 데이터 부족을 AI로 메우는 길.

9.5 정직한 평가 + 로드맵

  • 공모전 단계: L1→L2(적응형) + 메뉴/리뷰 임베딩이 현실적. 설명가능(왜 이 빵집?)해서 심사·UX 유리.
  • 발전성: 피드백 쌓이면 L3 학습형 → "쓸수록 똑똑해지는 추천"으로 서사.
  • 트리는 해석가능이 강점(딥러닝 블랙박스와 대비) — 포폴에서 "왜 이 알고리즘" 설명하기 좋음.
📌 결정: 1차 목표는 L2 정보이득 적응형. 피드백 로깅과 메뉴·리뷰 임베딩은 발전 단계에서 검토한다.
