1왜 이 문서

공모전 심사의 서비스 발전성(지속·확장) 20점은 "이 서비스가 계속 굴러가고, 다른 지역으로 커질 수 있는가"를 본다. 빵모아는 데이터 파이프라인이 지역에 독립적이라 확장이 구조적으로 쉽다 — 그 근거를 정리한다.

✅ 핵심 주장: 대전을 "지역코드 하나"로 처리하도록 설계 → 다른 도시 = 코드값 교체 + 스크립트 재실행. 알고리즘·UI·파서는 그대로 재사용.

2데이터 파이프라인 (지역 독립적)

데이터는 빌드타임에 1회 수집·파싱 → JSON 저장 → 런타임은 읽기만. API 실시간 호출이 없어 빠르고 쿼터 부담이 없다.

scripts/prefetchTour.mjs → src/data/daejeonTour.json. 빨간 상자만 지역마다 갱신.

지금까지 파싱 결과 (대전)

186관광지+문화시설 노드
145운영시간 high 신뢰
25medium(요일·계절)
16low(기본창 fallback)

각 노드 = {id, name, lat, lng, image, addr, hours:{open,close,confidence,raw}, rest}. 음식점(맛집 360곳)은 M4에서 동일 방식으로 추가 예정. ← 여기 수치 누적

3데이터 업데이트 전략 ("주기적 갱신 필요한가?")

JSON은 스냅샷이다. 운영시간 변동·신규/폐업 장소가 생기므로 주기적 재수집이 맞다 — 단 실시간일 필요는 없다.

무엇이 변하나변동 빈도대응
관광지 운영시간·휴무드묾(계절·연 단위)분기~반기 재실행이면 충분
신규/폐업 장소가끔재실행 시 자동 반영
빵집(카카오) 개·폐업가끔수집 재실행
실시간 혼잡·웨이팅실시간이 파이프라인 대상 아님(별도·후속)
✅ 권장: ① 공모전은 제출(9/21)·최종(10/28) 직전 각 1회 재실행으로 최신화. ② 운영 단계는 월 1회 스크립트 재실행(idempotent, 저비용). ③ 자동화 원하면 GitHub Actions 스케줄(cron)로 재실행→커밋. ④ confidence:low 16곳은 수기 검토 후보 리스트로 관리.
⚠️ 실시간이 아니므로 "오늘 임시휴무" 같은 건 못 잡음 → 상세카드에 "영업정보는 방문 전 확인" 안내 + 전화 노출로 보완.

4전국 확장 시나리오

다른 도시로 넓힐 때 다시 만드는 건 데이터뿐, 나머지(파서·그래프 엔진·UI)는 재사용.

구성요소확장 시
관광공사 데이터 파이프라인🔁 지역코드 교체 + 재실행 (파서 재사용)
빵집 데이터(카카오)🔁 지역 키워드로 재수집
운영시간 파서 / 그래프 엔진 / 화면✅ 그대로
src/config/regions.js➕ 지역 항목 추가(이미 다지역 구조)
✅ 발전성 어필: "빵모아는 대전 특화지만 전국 프랜차이즈-없는 로컬 빵집 지도로 확장 가능. 확장 비용 = 지역당 1회 프리페치(약 500 API 호출) + 데이터 검수. 코드는 재사용."

5한계 · 리스크 (정직하게)

  • 빵집 영업시간 롱테일: 카카오 API에 시간 필드 없음 → 관광공사 미등록 빵집은 "확인 필요" 배지. 지역 확장 시에도 동일 갭.
  • 거리 실API 쿼터: 지역·사용자 늘면 카카오모빌리티/ODsay 호출량↑ → 프루닝·캐시로 관리(경로 그래프 문서 참조).
  • low 신뢰 16곳: 자연어 파싱 실패분 → 기본창 처리, 수기 검토 대상.
