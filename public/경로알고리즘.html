1지금 앱: 빵집 → 최근접 관광지 1곳 동작

현재 develop 지도에서 실제로 되는 것. 빵집을 클릭하면 그 집에서 가장 가까운 관광지 1곳을 골라 지도에 초록핀 + 리스트에 초록배지로 표시. 계산은 "거리 재기"뿐(경로선·순서 없음).

기본 지도엔 관광지 없음 → 빵집 클릭 시 1곳만. 다른 빵집 누르면 그 집 기준으로 교체.

실제 코드 (src/components/map/MapResult.jsx)

// 빵집 한 곳에서 가장 가까운 관광지 1곳 → { name, km, lat, lng }
function nearestAttraction(bakery){
  let best = null
  for(const t of TOUR_SPOTS){
    const km = haversineKm({lat:bakery.lat, lng:bakery.lng}, {lat:t.lat, lng:t.lng})
    if(!best || km < best.km) best = { name:t.name, km, lat:t.lat, lng:t.lng }
  }
  return best
}
// 유저가 실제로 클릭한 빵집만 → 그 집의 최근접 관광지 1개만 지도에
const clickedBakery = selectedBakeryId ? bakeries.find(b=>b.id===selectedBakeryId) : null
const nearbyAttractions = clickedBakery?.nearSpot ? [clickedBakery.nearSpot] : []
🟢 언제 충분: 후보가 "빵집1 + 관광지1"뿐이라 고를 게 없다 → 최적화·DP 불필요. 이 단계는 이 지식만으로 완성.

2거리 → 이동시간 + 계산 따라가기 동작

두 점의 위·경도로 거리(km)를 재고(Haversine), 속도로 나눠 분으로. §1의 최근접 계산도 이걸 씀.

① Haversine 실제 코드 (src/lib/distance.js)

const R=6371, rad=d=>d*Math.PI/180       // R=지구 반지름 km
function haversineKm(a,b){
  const dLat=rad(b.lat-a.lat), dLng=rad(b.lng-a.lng)
  const s=Math.sin(dLat/2)**2
        + Math.cos(rad(a.lat))*Math.cos(rad(b.lat))*Math.sin(dLng/2)**2
  return 2*R*Math.asin(Math.sqrt(s))          // 구면 최단거리
}
계산 따라가기 — 대전역(36.3316, 127.4342) → 성심당 대전역점(36.3320, 127.4335)
dLat≈0.0004°, dLng≈-0.0007° → 아주 작은 각 → haversineKm ≈ 0.08km
도보 이동시간 = 0.08 × 1.3(우회) ÷ (4km/h) × 60 = 약 1.6 → 2분.

② 모드별 시간 = 거리 ÷ 속도 코스에서 쓸 것

const SPEED={walk:4, car:24}, DETOUR=1.3   // km/h, 우회계수
function travelMin(a,b,mode){
  const km=haversineKm(a,b)*DETOUR
  if(mode==='transit') return Math.round(km/SPEED.car*60*1.4+6) // 근사(임시)
  return Math.round(km/SPEED[mode]*60)
}
💡 이 근사는 도보엔 충분히 정확(도보는 직선에 가까움). 하지만 자차·대중교통은 실제 도로·배차가 달라 부정확 → §10에서 실API로 교체.

4타원 프루닝 + 공식 설계 제안

관광지·빵집·맛집을 다 계산하면 느리고 API 쿼터도 터진다. 출발–도착 시간예산 타원 밖은 버린다.

타원의 뜻(초점=S,E): 어떤 장소 x를 들렀을 때 S→x→E 이동시간 합이 하루 예산을 넘으면 제외.
keep(x) ⟺ travel(S,x) + travel(x,E) ≤ 시간예산
예: 예산 6시간, S→x 3.5h + x→E 3h = 6.5h > 6h → x 제외 (들르면 귀가 못 함).
💡 왜 먼저? 뒤의 DP·거리API는 후보 수에 비례. 수백 곳 → 수십 곳으로 줄여야 빠르고 거리 API N² 호출도 감당(§10).

5왜 그리디만으론 부족한가 배경

"매 순간 가성비 최고를 집자"(그리디)는 당장은 좋아도 전체 최적은 놓칠 수 있다.

반례: 지금 A(가치3, 가까움)를 집으면, 다음 칸에서 진짜 좋은 Q(가치6)로 못 잇는 배치가 될 수 있다. 그리디는 앞 선택이 뒤를 망치는 걸 못 본다.
→ 그래서 모든 조합의 누적 가치를 한 번에 따지는 DP가 필요(다음 절).
💡 그리디·오리엔티어링은 직관·근사로는 유용하지만, 우리처럼 슬롯 순서가 고정이면 DP로 정확해를 그냥 낼 수 있다.

6★ DP 코어 — 레이어드 DAG 최장경로 핵심 제안

슬롯을 층(layer)으로 세우면, 코스 = "각 층에서 한 곳씩 골라 잇는 길". 누적 가치가 최대인 길을 DP로 정확히 찾는다.

점화식 (핵심)

// best[슬롯s][노드b] = b까지 왔을 때 얻을 수 있는 최대 누적 가치
best[0][b] = value(b)                       // 첫 슬롯
best[s][b] = value(b)
           + max( best[s-1][a] )  over 연결가능한 a  // 시각·시간창 OK인 a만
정답 = argmax best[마지막][*] → 역추적(backtrack)
계산 예제 (value: A3 B2 / P2 Q3 / X4 Y2)
슬롯노드best 계산값
1A / BvalueA=3 · B=2
2P2 + max(A3,B2)5
2Q3 + max(A3,B2)=3+36
3X4 + max(P5,Q6)=4+610 ✓최대
3Y2 + max(P5,Q6)8
역추적: X(10) ← Q(6) ← A(3). → 최적 코스 A→Q→X, 가치 10. 모든 조합(2×2×2=8가지)을 안 그려도 표 한 번에 정답.
🟢 왜 이게 정답인가: 슬롯이 순서를 고정 → "왼쪽에서 오른쪽" 한 방향 DAG. 각 노드까지 최적을 쌓아 올리면 전체 최적이 보장(그리디처럼 앞선택에 안 당함). 노드 수십 개라 브라우저서 즉시.

7GRASP — "새 코스 또" 다양성용 보조 제안

DP는 정답 1개를 준다. 근데 "다른 코스 보여줘"엔 매번 같으면 재미없다. → DP top-k 경로 중 상위에서 약간 랜덤.

💡 변형 3종(🚶여유·🎯알찬·🍽미식)도 여기서: value 가중치 λ만 바꿔 DP를 다시 돌리면 성격 다른 최적 코스가 나온다.

82-opt — 개념만 (코스엔 안 씀) 학습용

순서를 자유롭게 바꿔야 하는 문제(예: 외판원 TSP)에서 X자 동선을 펴는 기법.

🟢 왜 우리는 코스에 안 쓰나: 우리 코스는 슬롯이 순서를 이미 고정(오후→빵→관광→저녁→야경). 바꿀 순서가 없으니 2-opt가 할 일이 없다. → 개념만 알아두고 코스 계산엔 DP만 쓴다.

9시간축·귀가 + 의사코드 설계 제안

코스에 시계를 붙인다. 도착 시각이 운영시간 안이어야 하고 귀가(예: 8시)를 못 넘긴다. 이게 DP의 "연결 가능" 판정.

// 도착 시각 = 이전 출발 + 이동시간. 문 열기 전 도착하면 대기.
도착(n) = 출발(이전) + travelMin(이전, n, mode)
출발(n) = max(도착(n), open(n)) + dwell(n)
연결가능(a→b) ⟺ 도착(b) ≤ close(b)-dwell(b)  // 운영 종료 전 관람
                && 도착(E) ≤ 귀가시각            // 기차 데드라인
운영시간 데이터: 관광공사에 대전 관광지·음식점 운영시간이 자연어(10:00~17:00·상시개방·화~일…)로 있음 → 빌드 때 파싱해 {open,close,휴무}로 저장하는 별도 자산이 이미 있음(현재 develop 앱엔 미탑재). 코스 구현 시 재이식. 빵집 시간은 없으면 "확인 필요" 배지 + 항상 방문가능 처리.
